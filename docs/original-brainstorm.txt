对。那就不能把它做成“Agent 项目里顺便用了 K8s、顺便训了 LoRA”，而应该把它设计成一个真正的交叉项目：

# **MCP-AgentGym**

### **Kubernetes-Native Agent Post-Training and Serving Platform**

一句话定位：

> A production-grade platform for generating verifiable tool-use trajectories, post-training open-weight agents, and deploying them on Kubernetes with scalable inference, observability, and failure recovery.

这个项目的**核心身份**应该是：

> **Agent Post-Training Infrastructure**

这样三个岗位看到的重点分别是：

* Agent 岗：可靠的 tool-using agent、MCP、harness、eval、recovery；
* ML Infra 岗：Kubernetes、vLLM、GPU serving、autoscaling、observability、Slurm；
* Fine-tuning 岗：轨迹数据、SFT、DPO、可验证奖励、OOD evaluation。

当前 Agent 岗普遍不只要“会调用工具”，而是强调生产化 agent loop、异步后端、验证系统、eval、observability，以及 latency/cost/reliability trade-off。([Ashby][1])
ML Infra 岗则明显看重模型部署与调度、autoscaling、routing、runtime management、GPU scheduling、vLLM、Slurm 和系统可靠性。([Ashby][2])
Post-training/RL 类岗位强调的则是训练环境、可验证评测、实验设计，以及把方法真正落到 production training run，而不是只调用一次 `SFTTrainer`。([Anthropic][3])

# 三、Agent 岗需要你证明什么

## 1. 自己实现 Harness 核心

可以用 LangGraph做持久化和图编排，但不要让整个项目等于：

```python
create_react_agent(...)
```

你应该自己实现：

```python
class AgentHarness:
    async def plan(self, state): ...
    async def discover_tools(self): ...
    async def select_tool(self, state): ...
    async def execute(self, tool_call): ...
    async def verify(self, transition): ...
    async def recover(self, failure): ...
    async def decide_stop(self, state): ...
```

至少包含：

* Typed agent state
* Dynamic MCP tool discovery
* Tool schema validation
* Parallel read-only tool calls
* Retry、timeout、backoff
* Token和tool-call budget
* Checkpoint/resume
* Human approval
* Permission-aware execution
* Environment replay
* Post-action verification
* Automatic rollback
* Complete trajectory tracing

Agent 岗真正会在意的是：

> Agent 调错工具怎么办？工具超时怎么办？schema变了怎么办？执行成功但问题没解决怎么办？

不是“你用了几个 Agent”。

## 2. 做动态工具变化

这是项目里最能区分普通 Agent demo 的部分。

评测：

* Tool重命名
* Description改写
* Required argument增加
* Argument type改变
* 工具暂时不可用
* MCP Server返回malformed response
* 同功能工具增加干扰项
* Tool response被截断
* Tool执行超时

例如：

```text
get_pod_logs
      ↓
fetch_container_output

namespace: string
      ↓
namespace: string, container: string
```

比较 Base、Prompted、SFT、DPO 在变化后的表现。

这能证明你做的是**工具泛化和可靠性**，不是背工具名。

## 3. 有真正的Verifier

Verifier应该结合：

```text
Kubernetes state
Health endpoint
Prometheus metrics
Unit/integration tests
Expected root cause
Safety policy
Deployment version
Environment transition
```

而不是只让 GPT 判断“看起来应该修好了”。

# 四、Fine-tuning 岗需要你证明什么

## 1. 数据来自执行，而不是凭空生成

每条trajectory保存：

```json
{
  "incident_id": "oom-017",
  "initial_state": {},
  "available_tools": [],
  "tool_schema_version": "v3",
  "actions": [],
  "root_cause_prediction": "kv_cache_exhaustion",
  "resolved": true,
  "validation_passed": true,
  "unsafe_actions": 0,
  "invalid_calls": 0,
  "tool_calls": 7,
  "latency_seconds": 42.3,
  "reward": 1.65
}
```

轨迹来源：

* Strong teacher model
* Base open-weight model
* Human-designed gold trajectory
* Automatically perturbed failure trajectory
* SFT/DPO model在线重新rollout
* Harness/runtime failure产生的恢复轨迹

数据处理要展示：

* Deduplication
* Rejection sampling
* Difficulty balancing
* Incident-type balancing
* Length filtering
* Invalid-argument filtering
* Train/test contamination checks
* Dataset versioning
* Quality statistics

Fine-tuning岗位会非常在意你是否理解：

> **数据构造往往比Trainer本身更重要。**

## 2. SFT不能只训最终回答

建议训练目标包括：

* Tool selection
* Argument generation
* Next-action prediction
* Root-cause classification
* Continue/stop decision
* Failure recovery
* Verification decision

只对Agent输出token计算loss：

```text
Environment observation: mask
Tool response: mask
Assistant reasoning/action: loss
Tool call JSON: loss
```

至少进行：

* Base model
* Prompt-only baseline
* Raw trajectory SFT
* Verified trajectory SFT
* SFT + DPO

## 3. DPO数据要由环境结果构建

同一个初始状态下比较两条轨迹：

```text
Chosen:
inspect rollout
→ query GPU memory
→ identify OOM
→ lower concurrency
→ restart
→ validate

Rejected:
restart pod
→ restart again
→ inspect unrelated database
→ scale replicas
→ unresolved
```

Preference不只看是否成功：

```python
score = (
    2.0 * resolved
    + 0.5 * root_cause_correct
    + 0.4 * validation_passed
    + 0.2 * recovered_from_failure
    - 0.05 * unnecessary_calls
    - 0.3 * invalid_calls
    - 0.8 * unsafe_actions
    - 0.1 * excessive_latency
)
```

必须做的消融：

* Outcome-only preference
* Safety-aware preference
* Efficiency-aware preference
* Full multi-objective preference

## 4. 最好加一个小型GRPO实验

SFT + DPO已经足够作为项目主体，但为了冲post-training岗，建议最后做一个规模受控的GRPO实验：

* 只在确定性Simulator上运行；
* 只训练tool selection/action generation；
* Reward完全可执行验证；
* 比较DPO和on-policy RL；
* 不追求大模型或超大训练量。

这样你能说自己覆盖：

```text
Offline demonstrations → preference optimization → on-policy learning
```

而不是简历里写“RLHF”，结果只是跑了个DPO notebook。

## 为什么 SGLang 特别适合这个项目

Agent 请求通常会反复携带：

* 相同的 system prompt；
* 相同的 MCP tool schemas；
* 相同的历史 trajectory 前缀；
* 多轮 observation/action context；
* 多次候选 rollout。

SGLang 的运行时包含 RadixAttention 前缀缓存、continuous batching、paged attention、structured outputs、speculative decoding、prefill-decode disaggregation 和多种并行方式，非常适合研究这种**长共享前缀、多轮、多分支 Agent workload**。([GitHub][1])

它也原生支持 JSON Schema、regex 和 EBNF constrained decoding，并提供针对 Qwen、DeepSeek、Llama 等模型的 tool-call parser。对 MCP Agent 来说，这可以直接用于降低非法 JSON、错误参数和无法解析的工具调用。([SGLang Documentation][2])

另外，SGLang 支持在同一批请求中高效服务多个 LoRA adapter，并提供 LoRA 缓存、异步加载和 eviction policy。这样你可以同时部署 Base、SFT、DPO，甚至不同领域的 adapter。([SGLang Documentation][3])

# 正确的架构方式

定义一个统一的推理接口：

```python
from abc import ABC, abstractmethod
from typing import Any


class InferenceBackend(ABC):
    @abstractmethod
    async def generate_action(
        self,
        messages: list[dict[str, Any]],
        tools: list[dict[str, Any]],
        adapter: str | None = None,
    ) -> dict[str, Any]:
        ...

    @abstractmethod
    async def health_check(self) -> bool:
        ...

    @abstractmethod
    async def load_adapter(self, name: str, path: str) -> None:
        ...
```

然后实现：

```text
InferenceBackend
├── VLLMBackend
├── SGLangBackend
└── APIModelBackend       # teacher / upper-bound baseline
```

Harness 完全不关心底层是谁：

```text
Incident
   ↓
Agent Harness
   ↓
InferenceBackend
   ├── vLLM
   └── SGLang
   ↓
MCP Tool Call
   ↓
Kubernetes Environment
```

这会证明你理解：

* backend abstraction；
* model-serving接口；
* runtime compatibility；
* failover；
* workload-specific benchmarking；
* 推理引擎与 Agent orchestration 的职责边界。

# vLLM 和 SGLang 分别负责什么

## vLLM：稳定基线和通用Serving

用来展示：

* OpenAI-compatible API；
* tool calling；
* structured outputs；
* continuous batching；
* 动态 LoRA adapter 加载；
* 多 LoRA serving；
* Kubernetes部署。

vLLM目前支持 named、auto、required、none 等工具选择模式，并能动态加载 LoRA adapter，很适合作为成熟的生产Serving基线。([vLLM][4])

## SGLang：Agent优化后端

重点展示：

* RadixAttention与共享前缀复用；
* 长tool schema场景；
* 多轮Agent trajectory；
* structured generation；
* reasoning/tool parser；
* multi-LoRA batching；
* speculative decoding；
* prefill/decode优化；
* Agent rollout吞吐。

所以不要简单写：

> Used both vLLM and SGLang.

而要写：

> Designed a pluggable inference layer and characterized when prefix-aware SGLang serving outperforms vLLM for multi-turn tool-using agent workloads.

当然，只有实验真的支持时才能写“outperforms”。没跑出来之前写成：

> Benchmarked vLLM and SGLang under multi-turn, shared-prefix agent workloads.

```text
├── agentgym-sft
├── agentgym-dpo
├── infra-specialist
└── coding-specialist
```

让每个请求动态选择adapter，测：

* 单adapter吞吐；
* 多adapter混合batch；
* adapter切换开销；
* cold/warm adapter latency；
* GPU/CPU adapter缓存；
* adapter数量对显存的影响；
* Base、SFT、DPO同时在线A/B evaluation。

SGLang支持同一batch内使用多个LoRA，并提供adapter加载和淘汰配置，因此这个实验既覆盖Fine-tuning，又覆盖Serving。([SGLang Documentation][3])

## 4. Backend故障转移

Kubernetes中分别部署：

```text
inference-vllm
inference-sglang
```

Gateway维护：

```text
Primary: SGLang
Fallback: vLLM
```

模拟：

* Pod被删除；
* readiness probe失败；
* OOMKilled；
* 请求timeout；
* engine返回malformed tool call；
* adapter加载失败；
* queue overload。

流程：

```text
SGLang request timeout
→ circuit breaker opens
→ request routed to vLLM
→ trajectory continues
→ Kubernetes replaces SGLang Pod
→ readiness passes
→ traffic gradually restored
```

指标：

* failover success；
* interrupted episode rate；
* recovery time；
* duplicate tool-call rate；
* p95 latency during failure；
* trajectory consistency。

这个实验对ML Infra岗非常有杀伤力，因为不是只比较tokens/s，而是在测**有状态Agent工作负载的Serving可靠性**。

### Agent岗

* long-context agent execution；
  -多轮前缀复用；

SGLang帮助你展示：

* multi-LoRA；
* Kubernetes GPU deployment；
* inference routing；
* backend failover；
* TTFT、吞吐、尾延迟profiling。

SGLang帮助你展示：

* 多adapter A/B evaluation；
  -训练后模型的Serving行为是否退化；
* tool validity与task success是否一致提升。

# 技术优先级

建议最终这样排序：

1. **自定义Agent Harness + MCP**
2. **可执行Kubernetes环境与Verifier**
3. **QLoRA SFT + DPO**
4. **SGLang + vLLM双后端**
5. **Agent-specific serving benchmark**
6. **Kubernetes failover与observability**
7. GRPO
8. Dashboard

SGLang应该加，但不要让你同时维护两套完全不同的业务逻辑。两种引擎都暴露OpenAI-compatible接口，上层统一。
